# dwa: terminal workspace for Claude Code agents (MVP plan)

## Context

The goal is an open source terminal workspace that runs a main Claude Code session plus several agent sessions in tmux, with a dashboard, where agents and the user can message each other, ask questions, report progress and wait on decisions, in parallel.

Decisions made: MVP is **workspace + messaging** (workflow engine and shared memory come later), **Claude Code only** behind a provider interface, name and command **`dwa`**, license **MIT**, runtime **Bun + TypeScript**.

The plan was written and tested against Bun 1.4.3, Claude Code 2.1.331 and tmux 3.8.

## Survey: what the research changes in the original document

1. **Claude Code now ships much of the plumbing natively.** The original plan predates this and would rebuild it.
   - Cross-session messaging (`ListAgents`, `SendMessage`, per-session inbox socket; an idle session gets a new turn started). Stable, local, on by default since 2.1.224.
   - 33 hook events, including `Stop`, `Notification` (`permission_prompt`, `idle_prompt`), `PermissionRequest`, `SessionStart/End`, `SubagentStop`. Hook types include `command`, `http`, `mcp_tool`.
   - Statusline JSON with context window %, cost and 5 hour / 7 day subscription limits. This covers the "context usage" panel without estimates.
   - `claude agents --json` lists sessions with `busy / waiting / idle`.
   - So dwa should be a **thin layer over native primitives**, not a parallel infrastructure. Anthropic keeps shipping first-party versions of these features, so thin also means less to throw away.
2. **Not building on:** agent teams (experimental, one team per session, no resume, state files not meant to be edited), channels (research preview, custom channels show a confirmation dialog on every launch), background sessions `claude --bg` (headless under Anthropic's supervisor, not panes you can type into). Worth watching, not depending on.
3. **Subscription login.** Anthropic's legal page allows an end user to sign in to the unmodified Claude Code binary with their own plan, and does not allow third-party tools to route requests through plan credentials. So dwa only launches the native interactive `claude` and never uses `claude -p` or the Agent SDK to drive agents. Also: "Claude Code" must not be part of the product name; `dwa` is fine.
4. **Terminal composition: tmux hybrid wins.**
   - tmux owns persistence and renders the native sessions; our TUI runs only in the dashboard panes. Lowest effort, highest fidelity.
   - Owning the whole screen with OpenTUI's embedded terminal (Ghostty VT) is possible now, but we would have to build persistence, reattach and key passthrough ourselves. Kept as a later option.
   - Require **tmux 3.7+** (synchronized output; older versions flicker with Claude Code). Use a private server (`tmux -L dwa -f <our conf>`), so your own tmux config is never touched.
   - **Claude Code renders badly below about 80 columns.** Twelve live mini-panes on the right, as in the sketch, will not work. See "Layout" for what replaces it.
5. **Prior art** (claude-squad, workmux, herdr, Gas Town, overstory, agent-deck, ccmanager and others):
   - Reliable: tmux session per agent, hook-driven status, a daemon or database as source of truth.
   - Fragile: detecting state by reading the screen (herdr broke on a Claude Code update), raw `send-keys` (lost newlines, swallowed Enter), large role swarms (cost, merge conflicts; overstory is archived, Gas Town "fell apart").
   - Already common, not worth rebuilding: session dashboards, worktree per task, usage viewers (ccusage).
   - Gaps dwa can fill: a first-class **question and decision queue** between agents and the user, hook-based state that survives CLI updates, and later deterministic workflows on top of interactive sessions (nobody does this).
6. **Dashboard library:** OpenTUI core (`@opentui/core`, 0.9.x, used in production by opencode), pinned to an exact version because it is pre-1.0.

## Architecture

```
tmux -L dwa (private server, generated config)
├─ window "workspace"
│   ├─ left pane   : dwa ui status   (OpenTUI)
│   ├─ centre top    : native `claude` main session (always visible)
│   ├─ centre bottom : the selected agent's native `claude` (only while an agent is selected)
│   └─ right pane  : dwa ui agents   (OpenTUI)
└─ window "pool"   : one parked pane per unselected agent, each a native `claude`

dwa daemon (Bun, one per project)
├─ Unix socket API (HTTP + WebSocket) used by the CLI, the UI panes, hooks and the MCP shim
├─ SQLite (bun:sqlite): agents, events, messages, questions
├─ tmux driver (plain tmux CLI calls; control mode only if needed later)
└─ provider interface → claude provider (launch flags, generated settings, hook mapping)
```

- **Layout.** The main session is **always visible** at the top of the centre column and never moves. The right pane is a list of agent tiles (name, role, state, current activity, "needs you" marker), not live terminals. It shows **only active agents** (sessions that are running): no empty slots and no placeholders for roles that have not been started. At most 12 tiles are visible at once; with more, the list scrolls (mouse wheel, `j/k` or arrows when the pane has focus) and the header shows the count, for example `AGENTS 5` or `AGENTS 1–12 of 15`. A stopped agent's tile disappears; with no agents the pane shows a one-line hint on how to spawn one. Selecting an agent opens its native session in a pane **under the main session** (`join-pane -v` from the pool into the centre column, full centre width so it stays above 80 columns). Selecting another agent swaps it into that same lower pane (`swap-pane`); closing the lower pane sends the agent back to the pool, still running, and main gets the full height again. Default split is about 60% main / 40% agent, resizable, and `Alt+z` zooms whichever pane has focus.
- **Launching a session.** `<profile command> --setting-sources project,local [--tools <list> | --disallowedTools <list>] --session-id <uuid> --name <name> --settings <generated.json> --strict-mcp-config --mcp-config <generated.json> --append-system-prompt-file <generated.md> [--permission-mode <mode>] [--plugin-dir <dir>]... [--model <m>] [--effort <e>]` with `DWA_AGENT_ID` and `DWA_SOCKET` in an otherwise cleaned environment (no inherited `CLAUDE*` or `TMUX` variables), plus `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0`, `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=0` and a very large `MCP_TOOL_TIMEOUT` so a blocking `ask` is not cut short. The generated files live in `.dwa/run/agents/<id>/`. Nothing is written to your `~/.claude` or the project's `.claude/settings.json`.
- **Giving a session its task.** The task is not a launch argument: a prompt given that way is taken before the MCP servers have connected, and the session starts without the dwa tools (docs/spikes.md, S8). The session's dwa MCP server tells the daemon when the session has connected to it (`POST /agents/ready`), and `Workspace.ready` then types the task into the prompt box a second later. A task whose session never reports in is typed in after 20 seconds, so it is not lost. A restart with `--resume` gives no task, the conversation has it; a session started afresh gets it again the same way.
- **Isolation.** A session does not get the user's own Claude setup; S5 in `docs/spikes.md` has the experiments. `--setting-sources project,local` drops user settings and with them hooks, status line, plugins, personal skills, commands and agents. `--strict-mcp-config` leaves only the servers of the generated MCP file: dwa's own, the role's servers from the catalogue, the project's `.mcp.json` servers and those of the role's plugins, which dwa copies in because strict mode would drop them. The generated settings add what flags cannot do: `claudeMdExcludes` for the personal `CLAUDE.md` of the profile's config directory, `autoMemoryEnabled: false` unless the role sets `memory`, `skillOverrides` set to `off` for project skills a role does not list and for built-in skills named in `off_skills`, `enabledPlugins` set to `false` for `off_plugins`, and the role's permission rules next to the always allowed `mcp__dwa`. Project servers from `.mcp.json` start without Claude Code's approval dialog, since they come in through the generated file. Built-in tools and skills are given, not taken away (S9): every session is started with `--tools` and a list, the role's or `DEFAULT_TOOLS`, so a tool Claude Code adds does not reach a session by itself and the definitions of the tools nobody listed are not sent; `tools = ["*"]` is the one case without a list. `skillOverrides` switches off every built-in skill dwa knows (`BUILTIN_SKILLS`) except those a role keeps with `builtin_skills`, and the session's `PreToolUse` hook refuses a `Skill` call for anything that is not in `skills.json` in its run folder (`ResolvedSession.allowedSkills`: its project skills, its dwa skills as `dwa:<name>`, kept built-in ones, `<plugin>:*` for its plugins), which is what covers a skill dwa has no name for. Neither list has `Agent` or `Workflow` unless the role sets `subagents`, because Claude Code's own system prompt and plan mode otherwise send work to hidden built-in subagents instead of workspace sessions. For the same reason `skillOverrides` switches off the built-in `code-review` skill (`SUBAGENT_SKILLS`): it runs as a background fork through the `Skill` tool and needs neither of the two tools. A skill file with `context: fork` would fork the same way, so `resolveSession` takes it out of the session's skills (`agentSkills`; a project skill is switched off by name, another is not linked into the generated plugin) and the system prompt lists it as a skill to start with `spawn_agent` and `skill`. That spawn makes the skill's file the task of an ordinary workspace session, which reads it and works in the open; the role is the request's, else the one the skill names with `agent:` if the workspace has it.
- **Configurable Claude command.** `claude` is only the default. The executable is set through named profiles, so different accounts or wrappers can be used:

  ```toml
  # ~/.config/dwa/config.toml (personal), overridable in the project's .dwa/config.toml
  default_profile = "me"
  [profiles.me]
  command = "~/claude_me"
  [profiles.work]
  command = "~/claude_work"
  ```

  - Selection order: per-agent setting (`profile = "work"` on an agent in `.dwa/config.toml`, or `dwa agent spawn --profile work`), then `dwa up --profile <name>`, then `DWA_CLAUDE_COMMAND`, then `default_profile`, then plain `claude`. Main and agents may use different profiles in one workspace.
  - `~` and environment variables are expanded; a profile may also carry extra `args` and `env`.
  - The command must accept the normal Claude Code flags and pass them through (a wrapper script that ends in `exec claude "$@"` works). dwa adds its own flags after the command and never assumes the binary is named `claude`.
  - `dwa doctor` runs `<command> --version` for every profile and reports a missing command or a too-old version. Each agent tile shows its profile when more than one is in use.

- **What a session gets.** `resolveSession` (`src/shared/roles.ts`) layers `[defaults]`, the roles a role extends, the role, and the values given for one session (config entry, workflow step, spawn request); a later layer replaces an earlier one, lists included, and the two tool lists count as one choice. The result is stored with the agent (`agents.launch`) and shown in short form in the panes. A spawn that comes from an agent through `spawn_agent` is marked `narrowOnly`: it may deny more tools and rules and keep fewer servers, plugins and skills, and is refused when it asks for more. A session whose role needs something this machine lacks (an MCP command, a plugin directory) is not started. Model and effort are passed as `--model` and `--effort` after the profile's arguments, so they win over a model set there; for the main session `[main]` wins over its role.
- **Roles are dwa's own files**: `.dwa/roles/<role>.toml` (and `~/.config/dwa/roles/` for personal ones), with the capability settings and a `prompt`. The prompt is appended to the system prompt after the workspace part (`--append-system-prompt-file`), so Claude Code's own system prompt is the same for every role; `--agent` and `.claude/agents/` are not used. The main session is a role too. Three more role-file fields are about handing work over and are not capabilities: `when_to_use` (what to hand to the role and what not; `description` stands in without it), `in_role_list = false` (the role is not offered) and `role_list = true` (sessions of the role are given the list of roles, after their prompt). `resolveSession` only decides whether a session gets the list (`roleList`, present only when on); the text is made by `src/shared/role-guide.ts` when the session's files are written, so a restart has the roles as they are then, and a role that changes does not make the sessions that list it out of date. `list_roles` gives the same list at any time. Skills from `.dwa/skills` and `~/.config/dwa/skills` reach a session through a plugin generated for it (a manifest and links, passed with `--plugin-dir`), where they are named `dwa:<skill>`.
- **Changing a running session.** The tools dialog (`src/ui/tool-screens.ts`, `Workspace.toolsInfo` / `saveTools`) turns switches into capability values (`src/shared/tools.ts`) and saves them in one of three layers: for the one agent (`agents.overrides`), for its role until the workspace stops (meta `role_run`), or into a role file or `[defaults]`. Resolution order is `[defaults]`, parents, role, the role's values for this run, what the session was started with (`agents.request`), the agent's own changes. A running session is compared with what it would be started with now (`liveBlocks`): when the difference only takes things away (tools, servers, single MCP tools), the list is stored in `agents.blocked` and written to `blocked.json` in the session's run folder, and the `PreToolUse` hook refuses those calls from that file (so it holds while the daemon is unreachable; an unreadable file refuses every call), because Claude Code does not re-read `--settings` and only a hook decides live (S6). Anything else is a restart: `respawn-pane -k` in the same pane with `--resume <session-id> --system-prompt-snapshot off` and newly generated files, after which the session gets a message saying what it has now. A restart always resolves from the files as they are. A busy session restarts only when told to, or at its next `Stop` (`agents.pending_restart`); the listener only enqueues.
- **Role files are edited in place.** `src/shared/toml.ts` finds the span of a key and replaces, inserts or removes it, item by item for lists written over several lines, then parses the result and refuses the write when anything else changed. `src/shared/role-edit.ts` is the only writer of role files and of `[defaults]`; every write goes through `saveTracked` (`src/shared/history.ts`), which first records what is on disk (an edit made by hand) and then the new content, as numbered versions under `.dwa/history/` with a pointer to the current one.
- **State.** Hooks call `dwa hook <event>` (command hook that forwards the JSON to the daemon socket). Mapping: `SessionStart` → started, `UserPromptSubmit`/`PreToolUse` → working, `Stop` → idle, `Notification(permission_prompt)`/`PermissionRequest` → needs user, `SessionEnd` → stopped. `dwa statusline` forwards the statusline JSON (context %, limits, cost) and prints the one line the daemon answers with (role, model, context, cost): Claude Code keeps a row for the status line even when the command prints nothing. No screen reading.
- **Messaging.** An MCP server (`dwa mcp`, stdio shim to the daemon, identifies the caller by `DWA_AGENT_ID`) gives every session these tools:
  - `list_agents`, `list_roles`, `spawn_agent(role, task, keep?)`, `stop_agent`, `finish_task(result)`
  - `send_message(to, body)`: fire and forget, to an agent or the user
  - `ask(to, question, options?)`: **blocks** until the other agent or the user answers; the answer is the tool result. The asker shows as "waiting on X" in the dashboard. **There is no timeout**: dwa never expires a question and never returns a default answer; a question stays open until it is answered or the user cancels it. It is stored in SQLite, so it also survives a daemon restart or a resumed session. The same holds for `wait_for`.
  - `report_progress(summary, percent?)`, `wait_for(agent | question)`
  - Questions addressed to the user land in a queue. The top bar shows how many are open, and a click on the count opens the queue (`answer`); they are also answered by focusing the agent and typing.
- **Handing work over.** A session that another session starts with `spawn_agent` owes it a result (`Delegation` in `src/daemon/delegation.ts`). The spawn request carries the caller's id (`from`), and so does `agent spawn` of the CLI when it is run inside a session (it then has the session's `DWA_AGENT_ID` and is narrow-only like the tool; `spawnOrigin`). The id is stored on the new agent's row (`agents.spawned_by`, with `keep`, `finished_at` and `reminders`), and the task gets a suffix that says who waits and how to report. The session ends its task only with `finish_task(result)`: the result goes to the spawner as a message, the user's inbox gets a line with its first line, and the session is stopped with `Workspace.stop` unless it was started with `keep`. Stopping deletes nothing, so the row keeps its session id and what it was started with. The end of a turn is not the end of the task: the session is reminded, at most twice since someone last spoke to it, then the one who waits is told once; a session that waits for an answer or for agents of its own is not reminded, and nothing ever stops a session that has not reported. When the spawner is gone, the result goes to the nearest session up the chain that still runs, in the end to the user. A report is refused while a question to the session is open. `wait_for` on an agent the caller started keeps waiting while reminders are due and returns the result itself once the session is gone (`Delegation.outcome`). Sessions the user starts, those of `[[agents]]` and workflow steps have no spawner and are untouched: `Delegation` acts only on rows with one, the workflow engine only on step agents.
- **Delivering a message into a running session** was settled by spike S3 (see [spikes.md](spikes.md)): (1) a mailbox hook: an `asyncRewake` command hook registered on `SessionStart` and `Stop` waits on the daemon and exits with code 2 when a message arrives, which wakes even an idle session; (2) `load-buffer` + `paste-buffer -p` + Enter as a fallback, only when hooks say the session is idle. Agents may also use Claude Code's native `SendMessage` with each other; the daemon sees those through hooks. Writing to the native inbox socket from outside is not used, its payload format is undocumented. The daemon hides this behind one `deliver(agentId, message)` function.
- **Keys.** A prefix key (`Ctrl+Q` by default, `keys.prefix` in the config), then `1..9` to open the agent at that visible position under main (agents further down are opened from the list or the palette), `0` focus main, `x` close the agent pane, `z` zoom, `d` detach. A prefix is the default because Alt/Option shortcuts do not reach the terminal on macOS layouts where Option types characters (Option+1 is `Ń` on the Polish layout). The same actions are also bound to Alt for terminals that send Option as Meta. tmux's default bindings are removed. Every shortcut is listed once, in `src/shared/shortcuts.ts`, with a label and a category: the tmux bindings, the comment in the generated config and the top bar's menus are all made from that list.
- **Top bar and menus.** One row across the whole window, above the three columns (`dwa ui topbar`, a full-width `split-window -fvb`, kept at one row by the `window-resized` hook). It shows the shortcut categories, the shell toggle, the counts of open questions and unread messages, and the keys. A click on a category asks the daemon (`POST /menu`) to run `display-menu` under the button, with the category's shortcuts as items. Like a popup it runs outside the tmux queue; unlike `display-popup` it returns at once (S10).
- **Wizards.** A wizard is a second OpenTUI program, `dwa wizard <kind>`, shown in a tmux popup: the pane asks the daemon (`POST /popup`), which runs `display-popup` outside its tmux queue because that command only returns when the popup closes. `src/ui/wizard.ts` is a small form engine (a stack of screens made of notes, buttons, inputs and choices, all clickable); `src/ui/wizards.ts` describes the screens and what each button asks the daemon, without terminal code. A wizard can end with a dwa command to run in the same popup, which is how editing a run reaches `$EDITOR`. The menu (prefix, then `p`) is one of these screens too; it replaced the earlier text menu.
- **Colours.** `src/ui/theme.ts` maps the four tones to entries of the terminal's 16-colour palette, so the user's theme decides the actual colours and they stay readable on its background. OpenTUI's named colour helpers are fixed RGB values (pure blue is `0,0,255`), which is what made text unreadable on some themes. The row that has the keyboard is drawn in inverse video and cursor marks use the terminal's own text colour, so nothing depends on a colour being visible.
- **Shell pane.** A plain `$SHELL` in its own pool window, shown in the slot under main like an agent (`Workspace.toggleShell`), so the two exclude each other. It is not an agent: no hooks, no MCP, no row in the store; only its pane id is kept (in `meta`) and it is forgotten when the user exits it.
- **Worktrees.** Off by default; a role can opt in and then the agent is started with native `claude -w <name>`. Merge handling is post-MVP.

## Workflow engine

Deterministic workflows on top of interactive sessions. The DAG runner, review loops and live editing are implemented. The control flow is the daemon's; the work inside a step is an ordinary agent session the user can open and type into.

- **Definition.** One TOML file per workflow in `.dwa/workflows/<name>.toml`: `[steps.<id>]` with `prompt`, and optionally `role`, `profile`, `model`, `effort`, `depends_on`, `keep_agent`, `reviews`, `max_rounds`. Prompts may use `{{input}}` and `{{steps.<id>.result}}` for steps they depend on. Validated with zod; unknown keys, unknown dependencies, cycles and placeholders for non-ancestors are errors.
- **Run.** `Workflows` in `src/daemon/workflows.ts` starts a step by spawning an agent (`Workspace.spawn`) with the rendered prompt as its task, as soon as all its dependencies are done. Independent steps run in parallel. Changes to runs go through the engine's own serial queue.
- **Completion is explicit.** A step ends when its agent calls the `complete_step(result)` or `fail_step(reason)` tool, or when its session is gone (failed). The end of a turn is not completion: the agent gets a reminder through the mailbox, at most twice, then the user is told and the step is marked as needing attention. There is no timeout. The user can close a running step by hand (`dwa workflow complete` / `fail`), with the same effect as the agent's call.
- **Failure.** After a failed step nothing new starts, running steps finish, pending ones are skipped, and the run ends as failed. No retries yet.
- **State.** `workflow_runs` and `workflow_steps` in SQLite. A run stores a snapshot of its definition, so editing the file does not affect it. On daemon start `resume()` fails steps whose session did not survive and starts steps that became ready.
- **Review loops.** A step with `reviews = "<step>"` may call `request_changes(feedback)` instead of completing. The reviewed step, the steps between it and the review, and the review each get a new row in `workflow_steps` with the next `attempt`; the engine only ever looks at a step's latest attempt, earlier ones are history. The session that did the reviewed step is not stopped while a review of it is open, so it receives the feedback as a message and does the next pass with its context; if it is gone, a new agent starts with the feedback and the previous result in its prompt. Every review pass is a new agent, told what the previous pass asked for. Validation requires every step that depends on a reviewed step to be an ancestor or a descendant of the review, so nothing runs beside the review on work that may be sent back.
- **The limit.** When a review asks for changes on pass `max_rounds` (default 3) or later, its step becomes `rejected` and the engine puts a question to the user (`another pass`, `accept`, `fail`) through the normal question queue, with the question id stored on the step. `Messaging.onQuestionClosed` tells the engine about the answer; `resume()` picks up a decision made around a restart. Like every question it never expires. The user can also decide with `dwa workflow complete` / `fail`.
- **Live editing.** `Workflows.edit(runId, toml)` replaces a running run's snapshot. The snapshot is turned into TOML by `formatWorkflow` (a small writer for this one schema; a test checks that parsing it back gives the same definition), so the user edits the run's own copy in `$EDITOR` (`dwa workflow edit <run>`) and agents use `workflow_definition` / `edit_workflow`. The new text goes through the same validation as a file. Then the two versions are compared step by step: an added step gets a pending row, a removed step loses its rows (and its agent), a step that has not started just follows the new text. A step that has started and whose work changed (`sameWork`: prompt, role, profile, model, effort, reviews, dependencies) gets a new attempt, and so does every started step that depends on it; their agents are stopped and the open attempt is closed as history. `keep_agent` and `max_rounds` are settings and never restart anything. A preview mode returns the list of changes without applying them, which the CLI uses to ask before work is thrown away. A run with a failed step is ending and cannot be edited. An edit by an agent is reported to the user.
- **Reporting.** When a run ends, whoever started it (the user or an agent) gets a message with the outcome. Runs are part of the workspace state the panes poll, and the status pane lists them. A click on a run or one of its steps there opens that run in the designer.
- **Events.** `Workspace.onAgentEvent` reports `turn_ended` and `stopped`. Listeners run inside the tmux queue, so they must only enqueue work and never wait on the workspace.

- **The designer's view of a run.** `Workflows.view(runId)` gives the run, its definition as plain TOML and a revision that names that text. `edit` takes the revision the new text was made from as `base` and refuses when the run's definition is no longer that one, so two editors cannot undo each other's work.
- **Workflows written by agents.** `Workflows.saveFile` (the `save_workflow` tool) writes a workflow file from a complete text: validated like a file, its roles must exist, the change gets a version with the agent as its source, and the user gets a message. A workflow that is new is shown in the designer popup; a changed one is not. `Workflows.author` starts a session of the `workflow-author` role with the user's description as its task.
- **Roles written by agents.** `RoleAuthor` (`src/daemon/role-author.ts`) is the same for roles: `author` starts a session of the `role-author` role with the user's description as its task, and `saveFile` (the `save_role` tool) writes the role file from a complete text, with a version that has the agent as its source, a message to the user that says what the role gives a session, and the role settings popup for a role that is new. Before anything is written the text is resolved as a session start would resolve it, with the text in the file's place (`checkRoleText`), so a parent, an MCP server, a plugin or a skill that does not exist is refused by the one set of rules. Unlike a workflow, which can only use roles that exist, a role file is what `narrowOnly` narrows: an agent that could write any role could give the next agent it starts anything. So `author` records the one role (place and name) its session was started for in the store's `meta` table, and `saveFile` refuses every other caller and every other role, the author's own included.

## Workflow files and the designer

- **Scopes.** Roles and workflows are items of a kind (`src/shared/scope.ts`): a file in the project's folder or in the personal one, addressed by name and source. What a session or a run uses is the winner: the project's item before a personal one of the same name, which is then `hidden`. Editors, stores, history and the file commands always name one file exactly (`personal:<name>`, `--personal`), so a hidden item can still be opened, moved and renamed. A move takes the history along.
- **One writer.** `src/shared/workflow-edit.ts` is the only code that writes workflow files, as `role-edit.ts` is for roles. Every operation of the designer is a function from a text to a text built on the in-place table edits of `src/shared/toml.ts` (`setKeys`, `addTable`, `removeTable`, `renameTable`, `moveTable`, `replaceInValue`), which change the lines concerned and nothing else, check the result by parsing it, and refuse shapes they do not know (inline tables, `[[arrays]]`, duplicate headers). Comments survive by construction. `formatWorkflow` writes a text afresh and is used for a run's own copy only.
- **The text is the state.** A designer session (`src/ui/designer-model.ts`) is the text being edited, the text it started from, and the texts to go back to. Undo is a stack of texts, a draft is that session as JSON under `.dwa/run/drafts/`, and a text with mistakes is still drawn: `checkWorkflow` returns the problems with the step and key each belongs to, and `looseSteps` reads what can be read.
- **The picture.** `src/shared/diagram.ts` is pure: steps go into layers by their longest path from a step without dependencies, in file order within a layer; lines are drawn with corners, a review as a lane at the right with its pass count. The result is a grid of cells with a tone each, plus the regions a click can hit (step, line, review, a place to put a step). `diagramText` prints it for `workflow show`; `src/ui/diagram-view.ts` puts it on screen as one piece of styled text in a box that scrolls both ways.
- **Mouse.** Pressing a step and dragging it shows the places it can go; letting go on one puts it there (`src/ui/designer-gesture.ts` turns a press and a release into an operation). The same places are reached with `m` and the arrows, which is also what remains when a terminal sends no drags. Proven in a real popup in S7 of `spikes.md`.
- **Screens.** The designer is a view beside the form engine: `createForm` (the row engine of `wizard.ts`) is mounted in its side panel, and the outcome `{ view }` hands the popup from a list of rows to the designer and back, so lists, names, history and the save screens are ordinary wizard screens (`src/ui/workflow-screens.ts`, `src/ui/run-screens.ts`) tested as data.
- **Runs.** A run opens in the same designer with its steps locked: the picture shows state, pass and agent, and is refreshed from `/workflows/view` every two seconds. "Edit" unlocks the steps; the text edited is the run's own copy. Saving previews the edit, then applies it to the run, to the workflow file, or to both. For the file, `conform(text, definition, renames)` changes the file's text until it says what the run's definition says, touching only what differs, so the file keeps its comments and layout.
- **Known limits.** A step renamed in a run and then saved to the file keeps its place and comments only when the rename was made in the same designer session; otherwise it counts as removed and added. Renaming or deleting a personal item cannot see other projects that use it; the screens warn instead.
